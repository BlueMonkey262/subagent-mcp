# Codex app-server adapter protocol

## Evidence and compatibility pin

This note is pinned to the locally installed `codex-cli 0.153.3` binary observed on 2026-09-04. The protocol shapes below come from that exact binary's successful outputs from:

```text
codex app-server generate-json-schema --experimental --out <temporary-directory>
codex app-server generate-ts --experimental --out <temporary-directory>
```

The binary advertises `stdio://` (the default), Unix sockets, and WebSockets as app-server transports. Its generated protocol is JSON-RPC-like but deliberately does **not** include a required `"jsonrpc": "2.0"` member. Requests are `{id, method, params?}`, notifications are `{method, params?}`, successful responses are `{id, result}`, and errors are `{id, error: {code, message, data?}}`. Request IDs may be strings or signed 64-bit integers.

Runtime wire probing did not complete in the available sandbox. App-server startup needs writable Codex state even when `sqlite_home` and `log_dir` are redirected; the sandboxed attempt failed with `failed to initialize sqlite state runtime under ~/.codex` / `Read-only file system`. Consequently, stdio record framing, event ordering, timeout behavior, exact runtime error codes, and the examples' observed values are **unverified**. Do not describe this note as an end-to-end trace. The message names and field types are verified against schemas generated by the binary itself.

## Adapter boundary

Keep this protocol behind a thin, versioned `CodexAppServerAdapter`. The rest of the MCP server should consume backend-neutral events and never depend on Codex method names or nested objects.

The adapter should own:

- process startup and shutdown;
- transport framing and strict message decoding;
- monotonically unique request IDs and an `id -> pending request` table;
- initialization state;
- `session_id <-> threadId` and active `turnId` tracking;
- conversion of notifications into neutral text/status/tool/approval events;
- responses to server-initiated approval requests;
- cancellation, process death, malformed-message, and version-mismatch handling.

At startup, record `codex --version` and compare it to the tested pin. A different version should produce a prominent compatibility warning (or fail in a strict mode), not leak new fields into the neutral layer. Decoders should ignore unknown object fields and unknown notification methods, while rejecting malformed required fields. Regenerate schemas and rerun conformance fixtures when bumping the pin.

## Lifecycle

### Initialize

The first client request is:

```json
{
  "id": 1,
  "method": "initialize",
  "params": {
    "clientInfo": {
      "name": "subagent-mcp",
      "title": "Subagent MCP",
      "version": "0.1.0"
    },
    "capabilities": {
      "experimentalApi": false,
      "requestAttestation": false
    }
  }
}
```

`clientInfo.name`, `clientInfo.version`, and `clientInfo.title` are required (`title` may be null). `capabilities` itself may be null. If it is an object, `experimentalApi` and `requestAttestation` are required; optional members are `mcpServerOpenaiFormElicitation`, `optOutNotificationMethods`, and `extensions`.

The schema-derived response shape is:

```json
{
  "id": 1,
  "result": {
    "userAgent": "<server user agent>",
    "codexHome": "/absolute/path",
    "platformFamily": "unix",
    "platformOs": "linux"
  }
}
```

After a successful response, send the parameterless notification:

```json
{"method":"initialized"}
```

Whether app-server rejects other requests before `initialized`, and the exact error returned, are **unverified**. The adapter should nevertheless enforce this order locally.

### Start a thread

Minimal useful request (all shown configuration fields are optional in the generated type):

```json
{
  "id": 2,
  "method": "thread/start",
  "params": {
    "cwd": "/absolute/workspace",
    "approvalPolicy": "never",
    "sandbox": "workspace-write",
    "ephemeral": true
  }
}
```

Important optional inputs include `model`, `modelProvider`, `serviceTier`, `runtimeWorkspaceRoots` (absolute paths), `approvalPolicy`, `approvalsReviewer`, `sandbox`, `permissions`, `config`, `baseInstructions`, `developerInstructions`, `personality`, `historyMode`, `dynamicTools`, and `selectedCapabilityRoots`. `permissions` and `sandbox` cannot be combined. `multiAgentMode` is deprecated and ignored by this version.

The result is `{ "thread": Thread, ...effective configuration }`. In addition to `thread`, the response requires `model`, `modelProvider`, `serviceTier`, `cwd`, `runtimeWorkspaceRoots`, `instructionSources`, `approvalPolicy`, `approvalsReviewer`, `sandbox`, `activePermissionProfile`, `reasoningEffort`, and deprecated `multiAgentMode`. Persist only `result.thread.id` as the Codex backend session identifier.

The server also defines a `thread/started` notification with `{ "thread": Thread }`. Response-versus-notification ordering is **unverified**; correlate by `thread.id` and tolerate either order.

`Thread` includes `id`, `sessionId`, `parentThreadId`, `preview`, `ephemeral`, `modelProvider`, `model`, timestamps, `status`, `path`, `cwd`, `cliVersion`, `source`, and `turns`, among other metadata. Codex-generated thread IDs are documented as UUIDv7. For `thread/start`, `turns` is documented to be empty.

### Resume a thread

Prefer the stable ID form:

```json
{
  "id": 3,
  "method": "thread/resume",
  "params": {
    "threadId": "019...",
    "excludeTurns": true
  }
}
```

`threadId` is required. Schema comments define three resume sources: ID, in-memory `history`, or rollout `path`; for a non-running thread precedence is `history`, then non-empty `path`, then `threadId`. `history` and `path` are unstable and should not be used by this adapter. If the thread is already running, the server rejoins it, and a supplied non-empty path is only a consistency check. Optional configuration overrides largely mirror `thread/start`.

The response repeats the effective thread configuration from `thread/start` and adds `initialTurnsPage`, `turnsBackwardsCursor`, and `itemsBackwardsCursor`. Prefer `excludeTurns: true` unless history is required, then hydrate via paginated thread methods. Resume behavior for unknown, deleted, or concurrently active IDs is **unverified**; propagate the structured server error and keep the neutral session unchanged.

### Start and observe a turn

Text input has a required `text_elements` array (snake case):

```json
{
  "id": 4,
  "method": "turn/start",
  "params": {
    "threadId": "019...",
    "input": [
      {"type":"text","text":"Implement the requested change.","text_elements":[]}
    ]
  }
}
```

`threadId` and `input` are required. Input variants include text, remote/local image, remote/local audio, skill, and mention. Optional per-turn overrides include `cwd`, workspace roots, approval policy/reviewer, sandbox policy or named permissions, model, service tier, reasoning effort/summary, personality, output schema, and collaboration mode. `permissions` and `sandboxPolicy` cannot be combined.

The immediate response is:

```json
{
  "id": 4,
  "result": {
    "turn": {
      "id": "019...",
      "items": [],
      "itemsView": "<view>",
      "status": "inProgress",
      "error": null,
      "startedAt": 0,
      "completedAt": null,
      "durationMs": null
    }
  }
}
```

The placeholder values illustrate the generated shape, not observed values. Store `result.turn.id` immediately. Turn status is one of `completed`, `interrupted`, `failed`, or `inProgress`.

Relevant server notifications are:

```json
{"method":"turn/started","params":{"threadId":"019...","turn":{"id":"019...","items":[],"itemsView":"<view>","status":"inProgress","error":null,"startedAt":0,"completedAt":null,"durationMs":null}}}
{"method":"item/started","params":{"threadId":"019...","turnId":"019...","item":{"type":"<variant>"},"startedAtMs":0}}
{"method":"item/agentMessage/delta","params":{"threadId":"019...","turnId":"019...","itemId":"019...","delta":"text"}}
{"method":"item/completed","params":{"threadId":"019...","turnId":"019...","item":{"type":"<variant>"},"completedAtMs":0}}
{"method":"turn/completed","params":{"threadId":"019...","turn":{"id":"019...","items":[],"itemsView":"<view>","status":"completed","error":null,"startedAt":0,"completedAt":0,"durationMs":0}}}
```

Treat `turn/completed` as the terminal event even if expected item notifications were absent. For failed turns, `turn.error` is populated; the server may also emit `error` with `{error, willRetry, threadId, turnId}`. Exact delta segmentation and notification ordering are **unverified**. The adapter should append deltas by `(threadId, turnId, itemId)`, deduplicate terminal events, and retain the completed item's canonical content where available.

### Interrupt

```json
{
  "id": 5,
  "method": "turn/interrupt",
  "params": {"threadId":"019...","turnId":"019..."}
}
```

Success is an empty result object:

```json
{"id":5,"result":{}}
```

The terminal turn should eventually have status `interrupted`. Whether the empty response precedes the terminal notification, repeated interrupts are idempotent, or unknown/already-terminal turns return success is **unverified**. Locally make cancellation idempotent: issue at most one interrupt for an active turn, continue draining notifications for a bounded grace period, then terminate the subprocess if required by the caller's cancellation deadline.

## Approval requests

Approvals are server-initiated **requests**, not notifications: they contain an `id`, and the client must reply with the same `id` and a `result`. Do not confuse that request ID with `threadId`, `turnId`, `itemId`, or optional `approvalId`.

### Current command approval

```json
{
  "id": "server-request-7",
  "method": "item/commandExecution/requestApproval",
  "params": {
    "kind": "<approval-kind>",
    "threadId": "019...",
    "turnId": "019...",
    "itemId": "019...",
    "startedAtMs": 0,
    "approvalId": null,
    "environmentId": null,
    "reason": "<optional reason>",
    "command": "git status --short",
    "cwd": "/absolute/workspace",
    "commandActions": [],
    "additionalPermissions": null,
    "proposedExecpolicyAmendment": null,
    "proposedNetworkPolicyAmendments": null,
    "availableDecisions": ["accept","acceptForSession","decline","cancel"]
  }
}
```

Only `kind`, IDs, `startedAtMs`, and `environmentId` are schema-required; the other fields above are optional. Reply, for example:

```json
{"id":"server-request-7","result":{"decision":"decline"}}
```

Command decisions are `accept`, `acceptForSession`, `decline`, `cancel`, `{"acceptWithExecpolicyAmendment":{"execpolicy_amendment":...}}`, or `{"applyNetworkPolicyAmendment":{"network_policy_amendment":...}}`. Only offer decisions present in `availableDecisions` when that field is provided. A headless adapter should default to `decline` unless its MCP caller explicitly supplies a permitted approval decision.

### Current file-change approval

```json
{
  "id": "server-request-8",
  "method": "item/fileChange/requestApproval",
  "params": {
    "threadId": "019...",
    "turnId": "019...",
    "itemId": "019...",
    "startedAtMs": 0,
    "reason": "<optional reason>",
    "grantRoot": null
  }
}
```

Reply with one of `accept`, `acceptForSession`, `decline`, or `cancel`:

```json
{"id":"server-request-8","result":{"decision":"decline"}}
```

`grantRoot` is explicitly marked unstable in the generated type, with a comment that it is unclear whether the grant is honored. Do not promise session-wide write grants.

### Legacy approval methods

The same 0.153.3 schema still includes legacy server requests `execCommandApproval` and `applyPatchApproval`. Their payloads use `conversationId`/`callId` and their decision vocabulary differs: `approved`, `approved_for_session`, `abort`, `timed_out`, `{"denied":{"rejection":"..."}}`, plus amendment variants. Implement these only as compatibility aliases translated immediately into the neutral approval model; never send current decision strings to legacy requests or vice versa.

Runtime production of current versus legacy methods under specific feature flags is **unverified**. Support both on input and select the reply vocabulary from the received method name.

## Failure handling and unverified behavior

The generated generic error envelope is:

```json
{
  "id": 4,
  "error": {
    "code": -1,
    "message": "human-readable message",
    "data": {}
  }
}
```

No exact runtime error code was observed. Preserve `code`, `message`, and opaque `data`; classify locally by operation and transport state rather than inventing meaning for numeric codes.

The implementation must explicitly handle:

- process spawn failure or early exit (capture bounded stderr, include observed CLI version);
- initialization timeout or rejection;
- malformed JSON / schema-incompatible messages;
- unknown response IDs and duplicate responses;
- request timeout, with late-response draining;
- server approval request while a turn is active;
- EOF before `turn/completed`;
- `error` notifications with `willRetry` true without prematurely finalizing the turn;
- terminal `failed`/`interrupted` turn statuses;
- resume failure without overwriting the caller's session mapping;
- cancellation races and duplicate terminal notifications.

**Still unverified and required before claiming full compatibility:** whether stdio is newline-delimited JSON versus another framing scheme; whether a literal `jsonrpc` member is tolerated; concrete startup and request error codes; notification ordering; interrupt races; approval timeout semantics; live current/legacy approval examples; and successful start/resume/turn traces. Capture these as golden transcripts in a writable, isolated Codex home/state environment before enabling this backend by default.
