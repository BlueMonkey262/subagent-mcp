# OpenCode server protocol note

Status: **partially verified against the installed binary**. The installed CLI is
OpenCode `1.17.6` at `<home>/.opencode/bin/opencode`. This note deliberately
distinguishes observations from the build brief's unverified wire-contract
claims. Do not turn a claim labelled **UNVERIFIED** into production behavior
without an integration probe or a schema generated by this exact version.

## Verified facts

The following came directly from the installed CLI on 2026-09-04:

- `opencode --version` prints `1.17.6`.
- `opencode serve` exists and is described as starting a headless server.
- Its relevant flags are `--hostname <string>` (default `127.0.0.1`),
  `--port <number>` (default `0`), `--cors <origin...>`, `--mdns`,
  `--mdns-domain`, `--print-logs`, `--log-level`, and `--pure`.
- `--pure` is accepted by `serve`; use it for deterministic adapter tests so
  user plugins cannot modify the protocol under test.
- When `OPENCODE_SERVER_PASSWORD` is absent, startup prints
  `Warning: OPENCODE_SERVER_PASSWORD is not set; server is unsecured.` This
  verifies that the variable controls a server security mode, but not the exact
  HTTP authentication scheme.
- With an isolated temporary `HOME` and XDG directories, startup tried to load
  (in order) `config/opencode/config.json`, `config/opencode/opencode.json`, and
  `config/opencode/opencode.jsonc` below the isolated XDG config directory.

## Port zero: not verified usable

Two sandboxed launches, one with port `0` and one with a fixed port, ended in an
opaque `ServeError` after config loading. This environment appeared to prohibit
binding a listener, so those failures do **not** establish whether port zero is
valid. The help text does establish only that `0` is the declared default.

The adapter must not assume that the bound port remains zero or that it can be
found from a stable stdout sentence. Before implementing dynamic ports, run an
unsandboxed loopback integration probe and capture the exact readiness line. If
the selected port cannot be parsed reliably, reserve an ephemeral loopback port
in the parent, close the reservation immediately before spawn, and pass that
explicit port (accepting the small bind race). A child that exits before
readiness is a startup failure and its captured stderr belongs in the error.

## Candidate REST/SSE contract from the brief (UNVERIFIED)

The build brief proposes this contract:

| Operation | Candidate endpoint | Candidate result |
|---|---|---|
| create session | `POST /session` | session object containing its ID |
| start a turn | `POST /session/{id}/prompt_async` | immediate acknowledgement |
| subscribe | `GET /event` | indefinite `text/event-stream` |
| reconcile | `GET /session/{id}/message` | authoritative message state |
| approve/deny | `POST /session/{id}/permissions/{permissionID}` | reply acknowledgement |
| interrupt | `POST /session/{id}/abort` | abort acknowledgement |

Every row above remains **UNVERIFIED against 1.17.6**, including method, path,
request body, status code, and response schema. In particular, the permission
reply route is a high-churn area: do not bake the brief's plural nested route
into the generic adapter interface. Keep all path and payload translation in
one version-specific transport module.

The following essential shapes are also **UNVERIFIED**:

- session create request fields (including cwd/project selection) and ID field
  spelling;
- `prompt_async` body, especially how provider/model, agent, system prompt, and
  user text/parts are represented;
- whether an async prompt returns JSON, boolean, or an empty success response;
- message and part discriminators, final assistant text extraction, usage data,
  and terminal error representation;
- permission request fields, legal reply values, and whether “always” is native;
- abort idempotency and behavior while a permission is pending;
- URL encoding rules and directory/project scoping headers or query params.

## Adapter contract to implement

This is the required behavior independent of the version-specific payloads.

### Startup and authentication

1. Create a per-process temporary runtime directory; launch in the requested
   child cwd with inherited permitted environment plus agent-specific env.
2. Run `opencode serve --pure --hostname 127.0.0.1 --port <resolved-port>`.
3. Generate a strong random password, set `OPENCODE_SERVER_PASSWORD`, and send
   credentials on every REST and SSE request. The brief says HTTP Basic, but
   that exact scheme and username are **UNVERIFIED**. Verify both before coding;
   fail closed rather than retrying unauthenticated.
4. Capture bounded stdout/stderr, wait for positive readiness, then perform a
   cheap health/schema request. Startup has a hard timeout and always reaps the
   process on failure.
5. Bind only loopback. Never expose an unauthenticated server on a non-loopback
   address.

### Spawn/resume

For spawn, create a session and retain both the OpenCode session ID and the
server-process identity. For resume, reuse the existing session and server when
alive. Persistence and the behavior after server restart are **UNVERIFIED**;
until tested, report a clear non-resumable/backend-lost error rather than
silently creating a fresh session.

Submit a turn asynchronously. Register the turn/session in local state *before*
sending the prompt, so an event arriving immediately cannot be orphaned. A
successful HTTP acknowledgement means accepted, not completed.

### Event ingestion and correlation

Treat `GET /event` as an optimization, not the source of truth:

- Parse SSE per the standard framing rules: accumulate multiple `data:` lines
  until a blank line, join them with newlines, ignore comments/heartbeats, and
  preserve `id:` for reconnect if the server supplies it.
- The exact event-name location and envelope are **UNVERIFIED**. Version-specific
  decoding must produce normalized `thread.started`, `message.delta`,
  `tool.start`, `tool.end`, `approval.requested`, `turn.completed`, and `error`.
- Correlate primarily by session ID, then message/part/tool-call/request IDs.
  Never correlate by arrival order: all sessions may share one event stream and
  tool/permission events can interleave.
- Deduplicate by stable event/part identifiers plus revision if supplied. If no
  event ID/revision exists, reconcile by authoritative entity ID and replace
  snapshots rather than appending duplicate text.
- Maintain exactly one reconnecting stream per server process. Reconnect with
  bounded exponential backoff and jitter. A disconnect is not turn completion.

The concrete SSE event envelope, event names, whether `Last-Event-ID` replay is
supported, and whether the stream starts with a connected sentinel are all
**UNVERIFIED**.

### Polling reconciler

Polling is mandatory from the first implementation:

1. Poll `GET /session/{id}/message` after prompt acceptance, periodically while
   running, immediately after reconnect, and before declaring a timeout/error.
2. Index messages and parts by stable IDs. Merge snapshots idempotently; do not
   assume list order or append-only responses.
3. Use SSE for low-latency deltas and polling to repair missing deltas, tool-end
   events, terminal messages, and permission requests.
4. A terminal assistant message plus backend idle/terminal state ends the turn.
   The exact terminal predicate is **UNVERIFIED**. Do not infer completion from
   a momentarily unchanged message list.
5. Apply a poll backoff while progress is observed, but retain a bounded maximum
   interval so a dropped approval event cannot hang indefinitely.

It is **UNVERIFIED** whether the message endpoint includes pending permissions.
If it does not, the adapter also needs the version's pending-permission list
endpoint; absence of both a stream event and queryable pending state is a known
protocol limitation that must surface as a watchdog timeout.

### Permission lifecycle

On a decoded permission request:

1. Key the parked request by the backend permission/request ID; also store
   session ID, message ID, tool call ID, permission kind/pattern, metadata,
   command/path/cwd, and child-supplied reason when present.
2. Run static and heuristic policy. If unresolved, emit one normalized
   `approval.requested` and return `needs_approval` to the parent.
3. Start the bridge watchdog immediately. The brief says OpenCode itself has no
   timeout; that is **UNVERIFIED**, so the bridge timeout remains authoritative.
4. Translate `allow`, `deny`, and synthetic `allow_for_session` in the
   version-specific layer. If the backend has no session-scoped decision, store
   the synthetic rule locally and send a one-shot allow.
5. POST exactly one reply. Mark resolved only after a successful response or an
   authoritative reconciliation showing it resolved. Duplicate parent calls
   return the stored result; they must not send a contradictory second reply.

Legal native decision strings, reply body, response body, and resolution event
are **UNVERIFIED**.

### Interrupt and teardown

Send the abort request, then continue SSE/poll reconciliation until the backend
reports a terminal/idle state or the abort grace period expires. Abort should be
locally idempotent. If the backend fails to settle, terminate the owned server
process gracefully, then force-kill after a short grace period. Reject all still
pending approvals with a stable `interrupted` reason. The HTTP response and
post-abort message state are **UNVERIFIED**.

## Failure modes the implementation must make explicit

- CLI absent or version different from the pinned version.
- listener startup failure, unreadable readiness output, port collision, or
  readiness timeout;
- authentication mismatch or accidental unauthenticated startup;
- non-2xx response, invalid JSON, schema mismatch, and HTML/proxy error bodies;
- SSE disconnect, malformed/truncated event, unknown event type, replay gap, and
  duplicate delivery;
- prompt accepted but no observable message; message polling unavailable;
- permission event dropped, permission request unqueryable, duplicate/late
  reply, reply rejected, or request disappearing before resolution;
- server exit during a turn; resume requested after process/session loss;
- user abort racing completion or approval;
- watchdog expiry while generating, parked on approval, aborting, or shutting
  down;
- unbounded transcript/event growth (retain bounded raw diagnostics and compact
  normalized state).

Unknown event kinds and additive JSON fields should be logged and tolerated.
Missing required correlation IDs or changed discriminators are protocol errors,
not silently ignored events.

## Version pin recommendation

Pin exactly `opencode==1.17.6` (or the distribution's equivalent immutable
artifact/version) for the first adapter. Check `opencode --version` at startup
and fail with an actionable mismatch unless an explicit unsupported-version
override is enabled. Keep one `v1_17_6` transport/codec module containing every
route, wire type, event discriminator, and decision translation. The generic
adapter must depend only on normalized events and operations.

Do not declare 1.17.6 supported yet. Promotion to “supported” requires a real
loopback integration fixture that records, with secrets stripped:

1. readiness and dynamic-port discovery;
2. authenticated and unauthenticated requests;
3. session creation and one async text turn;
4. full raw SSE frames plus authoritative message snapshots;
5. a real tool action that produces a permission request, both allow and deny;
6. interrupt while generating and while parked on permission;
7. resume in-process and, if claimed, after server restart;
8. concurrent sessions to prove correlation and deduplication.

Until that fixture exists, this document is an adapter design plus a verified
CLI/startup inventory—not a verified OpenCode 1.17.6 wire specification.
